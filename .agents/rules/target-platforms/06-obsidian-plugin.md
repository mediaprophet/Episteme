# Solid Obsidian Plugin Rules

Check `AGENTS.md` for the declared Deployment Target. When building an Obsidian plugin, you are bridging a sandboxed desktop environment with decentralized RDF graphs.

## 1. Authentication Flow (The Loopback / Custom URI)
- **Constraint:** Standard `window.location.href` redirects will attempt to navigate the entire Obsidian Electron window away from the user's vault, breaking the app.
- **Action:** You must use the system browser for the Solid-OIDC login page. To catch the redirect, you MUST either:
  1. Spin up a temporary local Node.js HTTP server (e.g., `http://127.0.0.1:45321/callback`) during the auth flow to catch the token, then close it.
  2. Use Obsidian's custom protocol handler (`obsidian://`) as the redirect URI (e.g., `obsidian://solid-auth-callback`).

## 2. Networking and CORS
- **Action:** If the target Pod server has aggressive CORS restrictions that block standard `fetch` from the `app://obsidian` origin, you can construct a custom fetch wrapper using Obsidian's built-in `requestUrl` API, which bypasses CORS entirely. 
- *Warning:* If using DPoP (Proof of Possession), ensure the cryptographic headers generated by `@inrupt/solid-client-authn-browser` are correctly passed through `requestUrl`.

## 3. Data Mapping: Vault to Graph
- **Action:** Obsidian stores data in flat `.md` files; Solid stores data in RDF graphs. You must use the Obsidian `Vault` and `TFile` APIs to read local content.
- **Rule:** Do not blindly upload `.md` files into the Pod as raw text. When instructed, parse the Markdown frontmatter (YAML) and transform it into a `SolidDataset` (RDF graph) before saving it to the Pod, ensuring true interoperability.

## 4. Session Persistence
- **Action:** Do not use `localStorage`. Store the serialized Solid session tokens securely in the plugin's `data.json` using the Obsidian `Plugin.saveData()` API, so the user doesn't have to log in every time they open their vault.
